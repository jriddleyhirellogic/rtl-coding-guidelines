# DO-254 Design Assurance (`DO_*`)

RTCA/DO-254 (*Design Assurance Guidance for Airborne Electronic Hardware*) is a **process**
standard, not a coding standard. It never says "do not use latches". What it says is that you must
have a coding standard, apply it, and show evidence that you did — and that the design implements
its requirements and **nothing else**.

In practice, programmes converge on a similar rule set, because the same handful of RTL constructs
are the ones that make "the design does only what the requirements say" impossible to demonstrate.
That converged rule set is what this file captures.

## Design Assurance Levels

DAL is assigned by the safety assessment, from **A** (failure is catastrophic) to **E** (no safety
effect). DO-254 is generally invoked by certification authorities for **DAL A and B** complex
hardware; DAL C and below are commonly handled with a lighter process.

| DAL | Failure condition | Typical RTL obligation |
|-----|-------------------|------------------------|
| A | Catastrophic | Full rule set, elemental analysis, independence, advanced verification methods |
| B | Hazardous | Full rule set, elemental analysis, independence |
| C | Major | Coding standard + requirements-based test |
| D | Minor | Coding standard |
| E | None | Company practice |

Supporting guidance worth knowing by name: **EASA CM-SWCEH-001** and the FAA/EASA **CAST-27**
position paper, which set expectations for Level A/B complex hardware; and DO-254 **Appendix B**,
which describes the advanced verification methods (elemental analysis, safety-specific analysis,
formal methods) accepted as design assurance evidence at the highest levels.

> This file is engineering guidance for writing certifiable RTL. It is not a compliance
> position, and it does not substitute for your programme's own PHAC, hardware design standards
> and DER/certification-authority agreements. Where this file and your PHAC differ, the PHAC wins.

## Determinism

### `DO_NOLATCH` — No inferred latches, ever
**Kind:** process + structural · **Severity:** must · **DAL:** A, B, C
**Overlaps:** `NTL_STR47`, `NTL_STR48`, `NTL_NAM09`, `NTL_STR50`, `NTL_STR51`
**Why:** a latch is transparent for part of the cycle, so its behaviour depends on input timing
rather than clock edges. That makes the timing analysis case-dependent and the behaviour hard to
argue deterministic.
**RTL rule:** if a value must be held across cycles, use a flip-flop (`always_ff`), never a latch.
Latches appear in a certifiable design only as explicitly instantiated library cells — integrated
clock-gating cells above all — and never as code. Every `always_comb` must assign every output on
every path; make the compiler enforce it.

```systemverilog
// BAD — infers a latch when sel is neither 0 nor 1
always_comb
  case (sel)
    2'b00: y = a;
    2'b01: y = b;
  endcase

// GOOD — default assignment first, then override
always_comb begin
  y = '0;                       // every path assigns y
  case (sel)
    2'b00:   y = a;
    2'b01:   y = b;
    default: y = '0;
  endcase
end
```

### `DO_SYNC` — Fully synchronous design
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** `NTL_STR01`, `NTL_STR02`, `NTL_CLK01`, `NTL_CLK02`, `NTL_CLK03`
**Why:** asynchronous logic cannot be verified by static timing analysis, so you cannot show the
implementation meets its timing requirements across the environmental envelope.
**RTL rule:** one clock domain per block where possible, one clock edge (`NTL_CLK03`), all state
in edge-triggered flops. No delay lines (`NTL_STR28`), no pulse generators built from logic
(`NTL_STR29`), no ring oscillators (`NTL_STR71`), no self-timed circuits.

### `DO_NOGATECLK` — No logic-gated or internally generated clocks
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** `NTL_CLK04`, `NTL_CLK07`–`NTL_CLK12`, `NTL_CLK35`, `NTL_CLK49`, `NTL_CLK50`,
`NTL_CLK19`
**Why:** a clock built out of combinational logic carries glitches, and a clock derived from a
flop output creates a timing path the tools cannot constrain properly.
**RTL rule:** clocks enter the block on a port and go straight to clock pins. For power gating,
instantiate the vendor's integrated clock-gating cell (`NTL_CLK28`) — never an AND gate. For
slower rates, use a **clock enable** on a flop, not a divided clock.

```systemverilog
// BAD — internally generated clock, glitch-prone and unconstrainable
always_ff @(posedge clk) div2 <= ~div2;
always_ff @(posedge div2) count <= count + 1;

// GOOD — one clock, enable-based rate control
always_ff @(posedge clk) begin
  tick <= ~tick;
  if (tick) count <= count + 1;
end
```

### `DO_NOTRI` — No internal tri-states
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** `NTL_STR34`, `NTL_STR37`, `NTL_STR43`, `NTL_STR44`, `NTL_STR45`, `NTL_STR63`,
`NTL_CON28`
**Why:** a floating bus has no defined value, and contention has no defined value and burns
current. Neither is a state you can write a requirement for.
**RTL rule:** use multiplexers internally. Tri-states appear only at chip I/O, in instantiated pad
cells (`NTL_PAD*`), with the enable registered (`NTL_STR04`) and available at the core boundary
(`NTL_STR54`).

### `DO_NOX` — No X in synthesisable RTL
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** none in `NTL_*` — gap; see `AF_XASSIGN`, `FA_XPROP`
**Why:** `'x` means "synthesis may choose" — the implementation is licensed to do something the
RTL simulation did not do. That directly breaks the argument that the verified RTL and the
implemented hardware are the same design.
**RTL rule:** never assign `'x` in synthesisable code. Assign a defined safe constant instead.
Accept the small area cost.

### `DO_NOINIT` — No reliance on initial values or `initial` blocks
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** partially `NTL_RST02`, `NTL_RST03`
**Why:** signal initialisers and `initial` blocks work in simulation and on some FPGA families,
and do nothing on others. Behaviour that differs between the verified model and the device is
exactly what the standard exists to prevent.
**RTL rule:** all state comes up from an explicit reset. No `initial` blocks in synthesisable
code, no `logic x = '0;` initialisers on registers. (Memory contents loaded from a file are a
separate, documented case.)

## Reset

### `DO_RSTALL` — Reset all state
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** `NTL_RST02`, `NTL_RST03`, `NTL_RST20`, `NTL_DFT38`, `AF_NORESET`
**Why:** you must be able to state the device's condition after power-up and after any reset. A
register with no reset has no defined post-reset value to state.
**RTL rule:** every register gets a reset with a documented reset value. This is stricter than
commercial practice, where datapath registers commonly skip reset to save area.

### `DO_RSTSYNC` — Asynchronous assert, synchronous de-assert
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** `NTL_RST05`, `NTL_RST06`, `NTL_RST08`, `NTL_RST22`, `NTL_RST23`, `FA_RDC`
**Why:** a reset removed asynchronously can violate recovery/removal timing at some flops and not
others, leaving the design in a state no requirement describes.
**RTL rule:** use a reset synchronizer per clock domain: assert asynchronously, release
synchronously to that domain's clock. Generate resets in one place at the top (`NTL_RST22`,
`NTL_PAR18`); never gate a reset with functional logic (`NTL_RST08`).

```systemverilog
// Reset synchronizer — async assert, sync release, one per clock domain
always_ff @(posedge clk or negedge por_rst_n)
  if (!por_rst_n) {rst_n_meta, rst_n_sync} <= 2'b00;
  else            {rst_n_meta, rst_n_sync} <= {1'b1, rst_n_meta};
```

## State machines

### `DO_SAFEFSM` — FSMs must recover from illegal states
**Kind:** structural · **Severity:** must · **DAL:** A, B
**Overlaps:** none in `NTL_*` — gap; interacts with `AF_FSMREACH`, `AF_CASEDEF`
**Why:** single-event upsets and unexpected conditions can put an FSM into an encoding the
transition logic never intended. Left unhandled, the machine may never return to a defined state.
**RTL rule:** every FSM gets a `default:` that goes to a defined recovery or error state, and the
default branch must **not** be optimised away — many synthesis tools need `safe_fsm`/`safe_case`
or equivalent to preserve it, and you must check the netlist to confirm it survived.

Note the deliberate tension with auto-formal tools: `AF_FSMREACH` and `AF_CASEDEF` will report
these defensive branches as unreachable, and that is the *correct and expected* result. Waive
those findings with a reference to this rule; do not delete the defensive code.

```systemverilog
always_comb begin
  next = state;                 // default: hold
  unique case (state)
    IDLE: if (start) next = RUN;
    RUN:  if (done)  next = IDLE;
    default: next = IDLE;       // SEU recovery — required, do not delete
  endcase
end
```

### `DO_FSMENC` — Justify the state encoding
**Kind:** process · **Severity:** should · **DAL:** A, B
**Overlaps:** none — gap
**Why:** one-hot has more illegal encodings than binary (and so a larger SEU exposure), but
simpler decode. Either is acceptable; the choice needs a rationale on record.
**RTL rule:** state the encoding explicitly rather than letting synthesis choose, so the verified
RTL and the netlist agree on what the illegal states are.

## Requirements and traceability

### `DO_TRACE` — Every RTL construct traces to a requirement
**Kind:** process · **Severity:** must · **DAL:** A, B, C
**Overlaps:** none — gap
**Why:** this is the core of DO-254. Every line of the design must trace up to a hardware
requirement, and every requirement must trace down to design and to verification evidence.
**RTL rule:** tag modules and significant always-blocks with the requirement IDs they implement,
in a fixed comment format a traceability tool can parse.

```systemverilog
// REQ: HW-REQ-0142, HW-REQ-0143
// Transmit FIFO write pointer; wraps at DEPTH per HW-REQ-0143.
always_ff @(posedge clk or negedge rst_n) begin
```

Keep the format machine-readable and consistent — the traceability matrix is generated from it,
and an inconsistent tag is a finding at audit.

### `DO_NODEAD` — No unintended function, no dead code
**Kind:** process · **Severity:** must · **DAL:** A, B
**Overlaps:** `NTL_CON32`, `NTL_CON33`, `NTL_LAN15`; see `AF_DEADCODE`, `AF_STUCK`, `FA_UNREACH`
**Why:** "the design implements its requirements **and nothing else**" is the hardest obligation in
the standard. Logic with no requirement behind it is unintended function, whether it is reachable
or not.
**RTL rule:** no commented-out blocks, no debug logic without a requirement, no half-implemented
features, no unused ports, no untraceable parameters. Debug and test features need their own
requirements, and evidence that they cannot affect flight function.

### `DO_DERIVED` — Derived requirements go back to safety
**Kind:** process · **Severity:** must · **DAL:** A, B
**Overlaps:** none — gap
**Why:** implementation decisions that are not traceable to a higher-level requirement — FIFO
depth, timeout length, synchronizer stage count — are *derived requirements*, and DO-254 requires
them to be fed back to the safety assessment process.
**RTL rule:** when you pick a number, record it as a derived requirement with its rationale. A
magic number in RTL with no requirement behind it is a finding.

## Verification evidence

### `DO_ELEM` — Elemental analysis
**Kind:** process · **Severity:** must · **DAL:** A (commonly B)
**Overlaps:** none — gap; see `FA_UNREACH`
**Why:** elemental analysis is the DO-254 Appendix B method that shows requirements-based testing
actually exercised the implementation, element by element. In practice it means measuring
structural coverage of the RTL under requirements-based tests — not under directed tests written
to close coverage.
**RTL rule:** write RTL that can be covered by requirements-based tests. Deeply nested
conditions, wide unreachable case spaces and unconstrainable corner conditions all produce
coverage you then have to argue away. Where a hole is genuinely unreachable, a formal
unreachability proof (`FA_UNREACH`) is strong evidence for the waiver.

### `DO_INDEP` — Verification independence
**Kind:** process · **Severity:** must · **DAL:** A, B
**Overlaps:** none — gap
**Why:** at the top assurance levels, verification must be performed by someone other than the
designer.
**RTL rule:** affects working practice rather than syntax — but it means RTL must be readable by
someone who did not write it. Comments state *intent*, not restate the code. This is where the
`NTL_NAM*` naming rules and the `pol_stylgd_*` style guides pay for themselves.

### `DO_TOOL` — Tool assessment and qualification
**Kind:** process · **Severity:** must · **DAL:** A, B
**Overlaps:** none — gap
**Why:** a tool whose output you rely on without independently checking it may need qualification.
A linter that *finds* problems you then fix and re-verify is usually low-risk; a tool whose pass
result is your only evidence is not.
**RTL rule:** record tool name, exact version and configuration in the design record, and keep
them frozen for the life of the programme. A rule-set change mid-programme is a re-verification
event. This applies directly to the `NTL_*` waiver set: freeze it, version it, and review every
waiver.

### `DO_WAIVER` — Every waiver is justified and reviewed
**Kind:** process · **Severity:** must · **DAL:** A, B, C
**Overlaps:** none — gap
**Why:** a coding standard is only evidence if deviations are controlled. An unreviewed waiver
file is a finding at audit.
**RTL rule:** every waived check records the rule ID, the specific instance, the engineering
rationale, and the reviewer. Never waive by wildcard, and never waive a whole rule for a whole
block. Re-review waivers whenever the RTL or the tool version changes.
