VCS Coding Rules

Introduction

This chapter provides detailed reference information for the Leda VCS policy. The VCS simulator performs cycle-based optimizations. VCS performance algorithms accelerate the synthesis subset by inferring simulation objects into the simulation executable. It specifies a language subset that can be accelerated using cycle-based techniques. Many of the rules in this policy generate warning messages that point out Verilog coding styles that can prevent these optimizations.

All the rules in the VCS policy were derived from VCS training material. Because VCS is a Verilog simulator, the rules in this policy apply only to Verilog. The VCS policy includes the rulesets shown in Table 2.
Table 2: VCS Policy Rulesets
Ruleset
Description
"Race Ruleset" These rules detect RTL constructs that can cause race conditions.
"VCS PERFORMANCE Ruleset" These rules detect RTL constructs that can slow the performance of the VCS simulator.
"SystemVerilog Ruleset" These rules detect SystemVerilog constructs that are not supported by VCS 7.0.

Race Ruleset

The following rules are from the Race ruleset:

VCS_14

Message: Only non-blocking assignments allowed in sequential always blocks to avoid race conditions.
Description This rule detects blocking assignments in synchronous blocks. because they can cause race conditions. Blocking assignments must not be used when modeling synchronous elements such as flip-flops. This rule is flagged for unintentional latches also.
Policy VCS
Ruleset RACE
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

always @(posedge b)
begin
if (!rst)
c = 0; // FAIL
else
c = a; // FAIL
end

VCS_15

Message: Only blocking assignments allowed in combinational blocks to avoid race conditions.
Description This rule detects non-blocking assignments in combinational blocks because they get updated right away rather than at the end of the time step. Combinatorial assignments must use blocking assignments.
Policy VCS
Ruleset RACE
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

always @(b)
begin
if (!rst)
c <= 0; // FAIL
else
c <= a; // FAIL
end

VCS_17

Message: Regs must be assigned by one block only to avoid race conditions. Multiple drivers detected for <%item>.
Description This rule detects registers being assigned by two different blocks. This is a problem because when two different blocks drive the same register, the final result is non-deterministic.
Policy VCS
Ruleset RACE
Language Verilog
Type Chip-level
Severity Warning

Example

The following example of invalid Verilog code exhibits this problem: 

always @ (posedge clk)
         if (reset) q <= 1'b0; // FAIL

always @ (posedge clk)
         if (enable) q <= d;

VCS PERFORMANCE Ruleset

The following rules are from the VCS PERFORMANCE ruleset:

VCS_1

Message: Avoid asynchronous feedback loops

Description This rule detects asynchronous feedback loops in designs. Asynchronous feedbacks are not desirable because they can put the scheduler in an endless loop.
Policy VCS
Ruleset VCS PERFORMANCE
Language Verilog
Type Chip-level
Severity Warning

Example

The following example of invalid Verilog code exhibits this problem: 

module VCS_1(a,a1,clk, a2, b);
input a, a1, a2, clk;
output b;
wire sel, o1;

assign o1= (sel==1)?a:a1;
assign a = o1; // FAIL
assign a1 = b;

endmodule

VCS_12

Message: Use only non-blocking assignments without delays in always blocks

Description Delays in non-blocking assignments can degrade simulator performance.
Policy VCS
Ruleset VCS PERFORMANCE
Language Verilog
Type Block-level
Severity Warning

VCS_2_3

Message: Avoid using event trigger

Description This rule detects event triggers in always blocks. Event triggers in always blocks can shut off VCS optimizations.
Policy VCS
Ruleset VCS PERFORMANCE
Language Verilog
Type Block-level
Severity Warning

Example

The following example of invalid Verilog code exhibits this problem: 

module VCS_2_3(a,a1,clk, a2, b);
parameter DEL1=10;
input a, a1, a2, clk;
output b;

begin
-> event1; // FAIL
end

always@(posedge clk)
begin
->event2; // FAIL
b <= o1;
end
endmodule

VCS_3

Message: Avoid using n_output_gate

Description This rule detects n_output_gate declarations. The simulator specifies a language subset that can be accelerated using cycle-based techniques. It is best to avoid using n_output_gates because they can degrade simulation speed.
Policy VCS
Ruleset VCS PERFORMANCE
Language Verilog
Type Block-level
Severity Warning

endmodule

VCS_3_4

Message: Avoid using pass_switch

Description This rule detects pass switch declarations. Pass switches should be avoided where there are alternatives such as assigns. Using assigns instead of pass switch declarations improves simulation speed.

Ruleset VCS PERFORMANCE
Language Verilog
Type Block-level
Severity Warning

VCS_7_11

Message: Avoid disable statement in always construct

Description This rule detects disable statements in always blocks. Disable statements in always blocks should be avoided because they can shut off VCS optimizations.
Policy VCS
Ruleset VCS PERFORMANCE
Language Verilog
Type Block-level
Severity Warning

Example

The following example of invalid Verilog code exhibits this problem: 

module VCS_7_11(a,b,c);
input a,b;
output c;
reg c, l, m, n, o;

  input k, y;
  inout p;
  output t;
   begin
 t = k + y;
end
endtask

initial
begin
disable my_task ;
end
always @( b)
begin
disable my_task; // FAIL
end

endmodule

VCS_7_3

Message: Avoid using wait statement in always blocks

Description This rule detects wait statements in always blocks. Wait statements in always blocks should be avoided because they can shut off certain VCS optimizations.
Policy VCS
Ruleset VCS PERFORMANCE
Language Verilog
Type Block-level
Severity Warning

Example

The following example of invalid Verilog code exhibits this problem: 

module VCS_7_1(a,b,c);
input a,b;
output c;
reg c;

always @( b)
 wait (!b) #1 c = b; // FAIL

initial
begin
wait (!b) #1 c = b; // PASS
end


always @( b)
begin
   wait (!b) #1 c = b; // FAIL
end


initial
begin
  wait (!b) #1 c = b; // PASS
end

endmodule
