DesignWare Coding Rules

Introduction

This chapter provides detailed reference information for the DesignWare policy. The DesignWare policy contains rules for writing synthesizable RTL code intended for
high-quality parameterized macrocells.

This policy covers some of the guidelines used by the Synopsys DesignWare team. DesignWare is a comprehensive library of synthesizable implementation IP components and verification IP models that you can use to speed time to market and enhance the built-in quality of your designs. The DesignWare implementation IP library consists of high-performance, technology-independent components ranging from simple building blocks to complex macrocells.

Finite State Machine Recognition

Several of the rules in the DesignWare policy concern finite state machines. Leda can infer finite state machines (FSMs) from a design and apply rules to constrain the type of FSM accepted. Leda can identify FSMs that are developed using case statements to define the states and transitions. Leda does not recognize FSMs defined using if statements. Leda recognizes 1-process, 2-process, and 3-process FSMs as long as all processes are in the same block (architecture or module).

Note that all of the rules in this policy are for Verilog only. The DesignWare policy rules are organized into the rulesets shown in Table 2
Table 2: DesignWare Policy Rulesets 
Ruleset
Description
"Architecture Ruleset" These rules deal with architectural issues such as the use of buffers and gated clocks.
"Coding Style Ruleset" These rules concern coding style issues, such as writing Verilog in a way that will readily translate into VHDL.
"Combinatorial Ruleset" These rules cover combinatorial logic concerns.
"Instantiation Ruleset" These rules are for module instantiations.
"Module File Ruleset" These rules cover conventions for naming module files.

"Sequential Ruleset" These rules cover guidelines for using sequential logic in inferred hardware such as flip-flops and latches.

A_5C_R_B

Message: Gated clocks are not allowed in the design

Description Avoid gated clocks in your design. Clock-gating circuits tend to be technology specific and timing dependent. Improper timing of a gated clock can generate a false clock or glitch, causing a flip-flop to clock in the wrong data. Also, the skew of different clocks can cause hold time violations.Gated clocks also cause limited testability because the logic clocked by a gated clock cannot be made a part of the scan chain.
Policy DESIGNWARE
Ruleset ARCHITECTURE
Language Verilog
Type Chip-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module A_5C_R_B (A, B, Clk, C);
input A;
input B;
input Clk;
wire notClk;
output C;
reg C;

//gating clock

assign notClk = Clk & B; // FAIL

//using gated clock

always @ (posedge notClk)
begin
if (A == 1)
C = ~B;
end

endmodule

CS_5P_R_A

Message: No blocking assignments are allowed in a sequential block

Description Use non-blocking assignments in sequential processes. Restrict your use of blocking assignments to combinatorial processes and continuous assignments. A blocking assignment must evaluate the RHS arguments and complete the assignment without interruption from any other Verilog statement. One problem with blocking assignments occurs when the RHS variable of one assignment in one procedural block is also the LHS variable of another assignment in another procedural block and both equations are scheduled to execute in the same simulation time step, such as on the same clock edge. This rule is flagged for unintentional latches also.
Policy DESIGNWARE
Ruleset CODING_STYLE
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module CS_5P_R_A (A, B, clk, C);
input A, B, clk;
output C;
reg C;

always @ (posedge clk)
begin
if (A == 0)
   C = 0; // FAIL
else
   C = B; // FAIL
end
endmodule

CS_5P_R_B

Message: No non-blocking assignments are allowed in a combinatorial block

Description Use blocking assignments in combinatorial processes and continuous assignments. Restrict your use of non-blocking assignments to sequential processes. A non-blocking assignment evaluates the RHS expression of a non-blocking statement at the beginning of a time step and schedules the LHS update to take place at the end of the time step. A non-blocking assignment used for combinatorial circuits that have multiple assignments can cause simulation mismatches.
Policy DESIGNWARE
Ruleset CODING_STYLE
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module CS_5P_R_Bb (A, B, C);
input A, B;
output C;
reg C;

always @ (A or B)
begin
if (A == 0)
   C <= 0; // FAIL
else
   C <= B; // FAIL
end
endmodule

C_2C_R

Message: Missing or redundant signals in the sensitivity list of a combinational block. Signal <%item> is missing or redundant.

Description Synthesis tools infer combinational or latching logic from an always block with a sensitivity list that does not contain the Verilog keywords posedge or negedge. For a combinational always block, the logic inferred is derived from the equations in the block and has nothing to do with the sensitivity list. The synthesis tool reads the sensitivity list and compares it against the equations in the always block only to report coding omissions that might cause a mismatch between the pre- and post-synthesis simulations.
Policy DESIGNWARE
Ruleset COMBINATIONAL
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module C_2C_R (a, b, c);
input a, b;
output c;
reg c;

always @(a)
begin
c = a & b; // FAIL
end

endmodule

C_3C_R

Message: This code will infer a latch. Need to have a default for a case statement and a completely specified if statement

Description If an assignment is made in any branch of an if statement, it must be made in all branches to avoid latches. A default assignment before the if may also be used; in this case the default assignment must be clearly labelled as associated with the if. This applies to case statements also; do not confuse this with the "default case" rule (see example).
Policy DESIGNWARE
Ruleset COMBINATIONAL
Language Verilog
Type Block-level
Severity Error

Example

The following example of valid Verilog code shows how to avoid this problem: 

module c_3c_r;
reg b, a; 
// example of default assignment to avoid latch AND shorten code 
reg [1:0] c; 
always
case (c) 
	0: begin a = 1; b = 0; end 
	1: b = 1; 
	2: b = 0; 
	3: b = 1; 
endcase
endmodule

C_4C_R_A

Message: Case statements must have a default assignment to prevent latch inference

Description Use a default assignment in case statements to prevent latch generation. Do not use the full_case pragma.A full case statement is one in which all possible case-expression binary patterns can be matched to a case default. If a case statement does not include a case default and if it is possible to find a binary case expression that does not match any of the defined case items, then the case statement is not full.
Policy DESIGNWARE
Ruleset COMBINATIONAL
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module C_4C_R_A (A, ClkM, Z);
input A, ClkM;
output Z;
reg Z;

parameter S0 = 0, S1 = 1, S2 = 2, S3 = 3;
reg [0:1] Moorestate;

always @ (posedge ClkM)
  case (Moorestate)
    S0 : Moorestate <= (!A) ? S0 : S2;
    S1 : Moorestate <= (!A) ? S0 : S2;
    S2 : Moorestate <= (!A) ? S2 : S3;
    S3 : Moorestate <= (!A) ? S1 : S3;
  endcase

always @ (Moorestate)
  case (Moorestate) // FAIL
    S0 : Z = 1;
    S1 : Z = 0;
    S2 : Z = 0;
    S3 : Z = 1;
  endcase

endmodule

C_4C_R_B

Message: SYNOPSYS full case pragma in not allowed

Description A full case statement is one in which all possible case-expression binary patterns can be matched to a case item or case default. If a case statement does not include a case default and if it is possible to find a binary case expression that does not match any of the defined case items, the case item is not full.When the full_case pragma is added to a case statement header, there is no change in the Verilog simulation. However, synthesis tools interpret the full_case directive to mean that if a case statement is not full, the outputs are don't cares for all unspecified case items. If the case item includes a case default, the full_case directive is ignored. Therefore, during simulation, the output behaves as if it were latched, whereas, synthesis tools treat the output as a don't care for the same select-line combination for unmatched case items. This causes a functional mismatch between simulation and synthesis.
Policy DESIGNWARE
Ruleset COMBINATIONAL
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module C_5C_R;

reg [1:0] in , out;
reg [3:0] current_state , next_state;
parameter state1 = 4'b0001 , state2 = 4'b0010, state3 = 4'b0100, state4 
= 4'b1000;

always @(in)
begin
  case (in) // synopsys full_case
    0 : out = 2;
    1 : out = 3;
    2 : out = 0;
  endcase

  case (1) // synopsys parallel_case full_case

    current_state[0] : next_state = state2;
    current_state[1] : next_state = state3;
    current_state[2] : next_state = state4;
    current_state[3] : next_state = state1;
  endcase
end
endmodule

C_5C_R

Message: SYNOPSYS parallel case pragma in not allowed

Description Write Verilog case statements in VHDL style. That is, cover all cases with no overlap. Do not use the parallel_case pragma.A parallel case statement is one in which it is possible to match a case expression to only one case item. If it is possible to find a case expression that would match more than one case item, the matching case items are called overlapping case items and the case statement is not parallel.When the Synopsys parallel_case directive is added to the case header, the example can simulate like a priority encoder but infers non-priority encoded logic when synthesized if the case statement is not parallel (overlapping). This can cause mismatches between simulation and synthesis. Therefore, it is better to cover all cases in a parallel case without overlapping.
Policy DESIGNWARE
Ruleset COMBINATIONAL
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module C_5C_R;

reg [1:0] in , out;
reg [3:0] current_state , next_state;
parameter state1 = 4'b0001 , state2 = 4'b0010, state3 = 4'b0100, state4 
= 4'b1000;

always @(in)
begin
  case (in) // synopsys full_case
    0 : out = 2;
    1 : out = 3;
    2 : out = 0;
  endcase

  case (1) // synopsys parallel_case full_case

    current_state[0] : next_state = state2;
    current_state[1] : next_state = state3;
    current_state[2] : next_state = state4;
    current_state[3] : next_state = state1;
  endcase
end
endmodule

C_8C_R

Message: Avoid asynchronous feedback loop

Description Combinational feedback interferes with static timing analysis and synthesis. The combinational feedback circuits are sensitive to spikes. There are no timing checks like setups and holds available for the simulation. The behavior of the circuit is layout dependent. Combinational feedback loops disable the operation of static timing analysis tools. Simulation also takes longer than it would if you used predefined registers.To check this rule on the entire design you must specify a top design unit using the -top switch.
Policy DESIGNWARE
Ruleset COMBINATIONAL
Language Verilog
Type Chip-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module C_8C_R (A, B, clk, C);
input A, B, clk;
output C;
reg N, C;
wire D, E;

always @ (posedge clk)
begin
if (A == 0)
    N = 0;
else
    N = D;
end

always @ (N)
begin
C <= N;
end

assign E = A & E; // FAIL

assign D = ((A & B) | (N & E));

endmodule

S_2C_R

Message: Use rising edge flipflop.

Description To avoid inverters in the clock line, use falling-edge-triggered flip-flops only if absolutely necessary. Falling-edge-triggered flip-flops cause an inverter to be inferred in the clock line, which must be handled separately in the routing process. This is an error-prone process.
Policy DESIGNWARE
Ruleset SEQUENTIAL
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module S_2C_R (A, B, Clk, Cntl, Z, Z1);

input A, B, Clk, Cntl;
output Z, Z1;
reg Z, Z1;

always @ (posedge Clk or negedge Cntl) // PASS
begin
  if (!Cntl)
     Z <= 0'b1;
  else
     Z <= B;
end

always @ (negedge Clk or negedge Cntl) // FAIL
begin
  if (!Cntl)
     Z1 <= 0'b1;
  else
     Z1 <= ~ A;
end

endmodule

S_4C_R

Message: Avoid latch inferring in your design

Description Do not use latches in designs, unless they are necessary for project- specific reasons.In general, flip-flop based designs are easier to synthesize and analyze than latch-based designs. In flip-flop based designs, data outputs are synchronized to a clock edge and are stable after some specified delay of the clock edge. In latch-based designs, the data flows through the latch while the clock is active. Therefore, the data can only be safely used if it is stored in a latch that uses a second clock guaranteed to be stable during the active period of the first clock.This rule only checks at the module level. There is a similar rule in the Leda general coding guidelines policy that you can use to check the entire design.
Policy DESIGNWARE
Ruleset SEQUENTIAL
Language Verilog
Type Block-level
Severity Error

Example

The following example of invalid Verilog code exhibits this problem: 

module S_4C_R (Clk, D, Set, Q, Qbar);

input Clk, D, Set;
output Q, Qbar;
reg Q, Qbar;

always @ (posedge Clk) // PASS
begin
 if (Set != 1)
    begin
       Q <= D;
       Qbar <= ~ D;
    end
end

always @ (Set or D)
  if (Set)
    Q = D & Clk; // FAIL
endmodule
